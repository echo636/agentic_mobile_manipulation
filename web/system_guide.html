OMNIGIBSON · RGB MANIPULATION · ASTRA

我们的操作智能体，
从观测到执行是怎样运行的？

Astra 读取四向 RGB，自主选择动作和画面中的目标；Harness 通过 MCP 接收工具调用，执行器在 OmniGibson 中操作，再把新图像交回大脑。Original 与 Official 共享这个闭环，但采用两套不同的小脑实现。

01

完整闭环：一次动作穿过哪些模块

点击模块查看输入、职责和输出。切换方法，查看执行层与工具目录如何变化。两套方法都由模型决定下一步，不按预写任务脚本执行。

01 / 任务与实例

固定环境，把任务说明交给模型

队列选择 task、instance 301、seed 0。仿真和 MCP 准备完成后，启动 Astra 并开始 30 分钟实际执行计时。模型获得自然语言任务说明，但不能访问 BDDL 真值或自行重置场景。

新 RGB → 下一轮 Astra 决策 → 新工具调用；直到 finish 或预算终止 ↺

MCP 做什么

MCP 是模型与工具之间的标准协议。我们的 Server 使用官方 Python SDK 的 mcp.server.lowlevel.Server，通过 stdio 提供工具目录与调用结果；RGB 作为图片内容返回。

Server 把调用转发到本机 HTTP bridge。bridge 将请求排入队列，由持有仿真器的主线程执行，避免多个线程同时修改 OmniGibson。

Harness 做什么

Harness 是运行闭环的宿主：限制公开数据、校验工具参数与图像版本、管理预算、执行动作、记录证据、结束后独立评分。

act 的 primitive 值由 Astra 选择；Harness 根据该名字分发。MCP 本身不会识别物体、规划动作或判断任务完成。

目前实现的 MCP 传输是 stdio；内部 HTTP bridge 是我们自己的 RPC 服务，不等同于已经支持 MCP SSE / Streamable HTTP。两种方法都没有因为“Official”而换用 FastMCP。

每张图为 512 × 512，水平视场约 90°、俯角 20°。相机刚性跟随底盘，安装半径 35 cm，高度为机器人初始最高点上方 5 cm。

这是我们在仿真中建立的四向相机装置；不是“保留原装头部相机并转四次”。共用 render barrier，四图携带相同 capture_id 和 sim_step。

模型具体收到什么

自然语言任务、工具说明、四张 RGB、image_ref、方向、尺寸、时间戳、仿真步、revision，以及之前的模型消息和工具结果。

成功的动作返回“执行器操作完成”和新图像。失败时返回固定的错误码与说明，例如 navigation_unreachable、sampling_error。

第三人称相机仅用于回放。它的图像、目标世界坐标、地图、对象名和评分均不作为模型观测输入。

PUBLIC / 大脑可见

  • 任务文字、工具 schema、Original 的 Skill 文本
  • 动作完成 / 失败反馈与最新 revision
  • 自己的先前消息和工具调用历史
PRIVATE / 执行器或离线评分可用
  • 深度、相机内外参、对象身份与几何

  • Open / Inside / ToggledOn 等真实状态
  • BDDL 谓词、TaskMetric、最终 Q 分数

“异步观测”现在实现到了哪一步

start_observation → job_id→仿真主线程调度采集→get_observation → 4 张 RGB

异步入口是真实存在的：start 在处理请求时只登记作业并返回；get 的处理函数直接返回当前状态，不主动等待采集完成。但 RPC 仍可能排在正在执行的动作或采集之后。模型可以在提交和查询之间读取 Skill 等工具。但采集仍由仿真主线程完成，与 act 串行。正在执行长动作时，主线程不会同时进行另一轮独立观测。

每个动作结束后，Harness 仍同步采集四向新 RGB 并附在结果中；observe 也是同步入口。当前没有持续运行的独立相机生产线程，也不会把新图自动推送进一次已经开始的 LLM 推理。

因此目前是“支持异步提交与查询的观测任务 + 动作后同步刷新”。它还不等于持续并行感知。look 则明确转动底盘，不是环视采集，也不是机械臂伸手动作。

03

Tools、Skills、Primitives 分别是什么

Tool 是模型直接调用的接口；Primitive 是 act 里选择的动作；Skill 是模型可读取的工作方法文档。读取一个 Skill 不会自动执行一套动作。

模型可调用的 Tool作用与主要返回OriginalOfficial
start_observation提交四向采集作业，立即返回 job_id 与状态。有有
get_observation查询作业；完成后返回 RGB，并标明是否已过期。有有
cancel_observation请求取消未完成作业；不移动机器人。有有
observe同步取得当前四向 RGB；旧图像引用失效。有有

read_skill读取指定 Skill 或其允许的参考文档。有未开放
visual-manipulation

依据新鲜 RGB 选择目标、调用动作、检查返回图像；不能把工具成功直接当成任务成功。

visual-exploration

查阅已有方向，必要时改变视点或接近目标。区分看向某处、移动到某处与操作物体。

pick-and-place

组织接近、抓取、选择容器或支持面、放置、视觉复核等步骤；动作仍由模型逐次调用。

failure-recovery

依据错误和新图像调整策略，避免不变的重复操作；找不到受支持的替代方法时报告 blocked。

Skill 在运行开始时冻结并记录哈希。read_skill 只允许读取这一份 Skill 包，不是通用文件访问工具。当前没有显式 plan stack、长期 memory 工具或多 Agent 分工；模型利用对话历史连续决策。

04

操作对象是怎样被选中的

模型先在图像中认出目标，再输出一个点。模型不能直接提交“radio_89”之类的仿真对象 ID，也没有按物体名称搜索全场景的接口。

  1. Astra 选择动作与像素例如在 back 图像里选择红色收音机，输出 toggle_on、image_ref 和 [x,y]。坐标归一化为 0–1，左上是 [0,0]。
  2. Harness 校验图像是否仍有效revision 必须匹配，image_ref 必须来自当前 snapshot。同一旧图即使仍保存在磁盘，也不自动成为可用动作目标。
  3. 私有执行器把像素转成世界射线使用该像素的深度和相机参数反投影世界点，再沿射线查询可见 mesh，确定对象归属并校验深度一致性。碰撞射线另外保存为诊断，不因其差值直接更换操作对象。此处读取真值发生在小脑内部。
  4. 将内部对象引用交给具体动作Original 可以进一步使用点击世界点选择接近位置和局部放置面；Official 主要将绑定后的对象引用交给上游动作。
  5. 把操作反馈与新图像交回模型真实对象 ID、世界坐标和后端诊断保存在私有记录中；公开反馈经过过滤。
点选并不天然可靠。点击容器开口可能击中后面的地板，点击柜门边缘可能绑定相邻 mesh。深度与可见 mesh 不一致或对象歧义会触发 invalid_visual_target。该错误不等于模型一定认错，也不等于物体一定不可操作。

当前回放已在“调用前原图”上标出 navigate_to 的输入像素。红圈表示模型点了哪里，不是机器人最后站在哪里。最终底盘站位与路径仍主要保存在私有导航记录，尚未作为完整路径叠加展示。

05

Original：我们维护的小脑如何工作

Original 是混合实现：部分语义状态由官方接口改变，导航、携带、放置和恢复逻辑由本项目维护。它是理想化执行器，但仍存在几何采样和仿真失败。

导航：静态 GT 栅格 + 接近点选择 + 逐步底盘移动

RGB 点击点→世界表面点→附近可站立候选→GT 栅格路径→分步设置底盘位姿

将 OmniGibson 官方静态可通行图缩放到约 5 cm 分辨率，并按配置侵蚀以留出空间；这不是按机器人和携带物当前完整几何实时计算的占地。在目标附近生成候选接近点，检查投影、路径、距离和视野，选择可达的站位；随后沿路径以理想位姿控制逐步移动并转向。

这一策略参考 jinkai 导航 Harness 的 GT planning 思路，但用的是 OmniGibson 的栅格和本项目的底盘适配器。不是从当前 RGB 实时 SLAM 建图，也没有完整的动态障碍重新建图与全程碰撞规划。

接近点与实际移动

候选包含目标附近的多个方向和半径；当前还用四相机视锥、遮挡和 1.4 m 范围筛选。跟随速度上限约 0.5 m/s、转速 60°/s。

这些是我们设置的搜索与运动参数。候选被全部过滤时，可能在真正路径搜索之前就返回 navigation_unreachable。

操作内部也可能移动

选择 grasp、open、toggle 等目标时，如果目标超出预设操作范围，Original 可以先自动接近，再操作。

因此一次 toggle_on 内部可能含底盘移动；仅看最外层工具名字，无法看出全部执行过程。

10 类 act 动作的实际实现

动作执行内容关键边界
navigate_to使用私有 GT 栅格规划接近点，分步设置底盘位置与朝向。点选位置不等于最终站位；静态图不保证所有动态障碍安全。
grasp当前默认 controlled carry：在目标原 XY 位置抬高 18 cm，保存相对底盘位姿，随后逐控制步更新物体及其刚性内容物。当前默认路径不调用官方 GRASP；无真实夹爪闭合，也不创建动态 fixed joint。
release解除本项目的携带约束，让物体释放并稳定。release 只负责松开，不指定目标表面或容器。
place_on_top围绕选中的表面点做局部射线采样，放置携带物、稳定并验证支持关系。可选相对世界竖直轴的 yaw 调整。不能直接跳到同一个柜子的任意另一层；局部候选与包络可能过保守。
place_inside通过官方 Inside 状态采样接口寻找容器内放置状态；本项目提供物理 tick 预算、底盘约束、携带物处理和检查。复杂容器、碰撞和采样可能失败；不是把物体无条件塞进容器。
open / close使用官方 Open.set_value(..., fully=True)，让抽屉等原有内容物随支持链接移动，稳定后验证；失败时可回滚。不要求大脑给出门把手轨迹；实际状态切换仍可能不成功。
toggle_on / toggle_off使用官方 ToggledOn 状态接口改变开关状态。“操作完成”只说明执行器步骤完成，不说明整个任务达成。
wait用保持动作推进仿真时间，默认 5 秒，可指定 0.1–20 仿真秒。这是我们提供的动作；不是让 LLM 睡眠，也不是所有官方动作的别名。

放置回退：为什么失败后物体可能又回到手里

Original 在放置前保存必要的世界状态与携带关系。如果采样失败或后置检查不满足，尝试恢复到放置前，避免把物体留在错误位置、掉落或破坏容器原有内容。这个“事务回退”是我们加的；它不是官方动作默认保证，也不能修复进程已经崩溃的情况。

Official：直接调用哪套官方动作

使用固定版本 OmniGibson 的 SymbolicSemanticActionPrimitives。它与主要面向运动规划的 Starter 动作类有关联，但本实验调用的是 Symbolic。

# 简化后的实际调用路径；obj 只在执行器内部存在
obj = resolve_current_rgb_pixel(target)
primitive = SymbolicSemanticActionPrimitiveSet[primitive_name.upper()]
generator = primitives.apply_ref(primitive, obj, attempts=1)
for action in generator:
    env.step(action)  # 同时计时、记录和检查
# release 不传 obj；完整实现还管理采样步数和异常。

我们仍负责的部分

RGB 观测与目标绑定、模型调用、MCP、预算、错误过滤、原始记录、回放和独立评测。还负责在固定依赖版本上初始化 CuRobo、适配上游签名并处理运行故障。

因此“直接调用”不意味着没有适配层。当前实际协议名为 rgb_official_symbolic_initialized_navigation_v2。

交给上游的部分

动作前置条件、原生对象处理与放置采样、语义状态设置、动作 generator、settling 和后置条件检查。

该路径不使用 Original 的自研 GT 导航、controlled carry、局部放置或失败状态回滚；也没有 Original 包装层的自动接近。

Official navigate_to 为何会“没动就超时”

  1. 选择靠近目标的机器人姿态官方流程围绕对象采样站位，并检查机器人碰撞与机械臂可达性；这部分使用场景真值和 CuRobo。
  2. 运行 DEFAULT / ARM 规划与 IK 检查当前初始化 DEFAULT、ARM 所需的规划器。Symbolic 的位姿终点移动不进入 Starter 的 BASE 轨迹规划器，因此没有为本路径分配不用的 BASE planner。
  3. 选定后直接设置导航终点位姿官方 Symbolic 导航是端点位姿设置，不是 Original 的逐段可视路径跟随，也不等价于连续的真实底盘控制。

如果候选位姿一直无法通过检查，可能耗时很久却没有一次 env.step。最近分析到的原生导航超时主要发生在可达性采样阶段；没有记录足够的 IK 拒绝细节时，不能进一步断言目标物理上一定不可达。

失败后的世界放置与受控状态操作有事务回退；失败仍不保证世界完全未变。无该回退；按上游实际执行结果保留状态。
动作预算通常最多 700 env steps；Inside 额外采样有独立 120 秒限制。原生动作主体有 120 秒合作式墙钟预算，同时受 env steps / 采样步数约束；单次 native 调用可能超时返回。
整任务预算当前队列为 30 分钟实际执行；初始化另计。另有 80 动作 / 240 工具调用 / 20,000 env steps 上限。
成功判定独立 BEHAVIOR / BDDL 任务评估。模型 finish 和单个动作 completed 都不直接等于任务成功。
工程定位探索可控、可诊断的理想化小脑适配。探索直接使用官方符号小脑的效果与限制。
如何理解当前实验：这是两套完整配置的比较。除了执行器，工具 / Skill / primitive 集合与动作预算也存在差异，而且历史尝试保留各自源码版本。当前结果不能直接解释为“只替换一个执行器导致了多少成功率差异”。

任务怎样被评测，什么才叫成功

当前比较选择 BEHAVIOR 的 100 个任务，使用 public_test、instance 301、seed 0。任务说明有 50 条来自官方 gallery、50 条来自项目对静态 BDDL goal 的翻译；这一差异记录在任务清单中。它是本项目的固定实验协议，不是正式排行榜提交。

TOOL

操作是否完成

例如 toggle_on 的状态操作成功，或 place_inside 的后置条件通过。只能说明单个执行步骤。

AGENT

大脑如何结束

模型调用 finish，声明 achieved、blocked 或 aborted，并给出视觉依据或受阻原因。

EVALUATOR

任务是否达成

独立检查任务的 BDDL 目标与 TaskMetric。最终任务成功和 Q 分数以该评估为准。

Q 来自官方 TaskMetric，用来记录目标进展；任务成功另由最终 BDDL 目标判断。运行故障可能让最终 Q 无法取得，此时不编造分数。整任务超时即使在最终状态保留了 Q=1，也仍可能被队列记为 timeout。

Q 的精确定义

官方任务成功时 Q=1；否则，对每个 goal option 统计“初始为假、最终为真”的谓词数，除以该 option 的全部谓词数，再取最大值。它不是“最终为真的所有谓词占比”，也不是模型自己给出的完成度。

队列与时间：一个任务最多运行多久

等待资源→仿真初始化 / MCP 准备→启动模型 · 30 分钟执行→独立评分 / 清理→CPU 发布回放

资源等待与仿真初始化不计入这 30 分钟。模型推理、观察、动作和执行期间的渲染开销都计入。初始化另有 watchdog；当前队列要求清单上的每条任务都有成功、失败或超时的终态，不能因一条普通任务失败就把后面的任务漏掉。

两种方法使用各自分配的资源池，可按 GPU 与主机内存条件多 worker 并行。任务按清单顺序领取，但并行时完成顺序可以不同。仿真退出后再释放对应资源，视频后处理由 CPU 队列继续完成。

任务结束、评分完整、录像生成完成是三个独立状态。已结束任务的回放可能仍在处理；若进程异常退出，可能只保留部分视频或没有视频。页面应如实展示，而不是用录像存在与否改变任务成绩。

原始信息如何变成可检查的回放

每条任务保存模型实际输出、工具调用与结果、四相机图像、动作时序、独立评分、源码与资产版本、主机 / GPU / PID 等信息。前端把同一时间轴上的观测、模型消息和动作结果同步展示。

模型的文本

保存模型实际返回的 assistant 消息、工具参数，以及供应端实际返回的 reasoning summary。回放按发生顺序累积展示这些记录。

没有返回的内部推理并不存在于日志中；不能补写，也不能把中文解释性摘要标成模型原始思考。

画面与时间

前视画面最大，其他方向与第三人称辅助展示。详读、连续仿真时间、墙钟等版本使用不同的播放时间映射。

仿真秒、真实墙钟秒、为了阅读插入的停留时间并不相同。应选择对应版本判断模型耗时或动作速度。

保存的内容用途
run.json / events.jsonl任务配置、状态、预算、动作与工具事件；区分公开反馈和私有执行细节。
model_events.jsonl / 控制器记录保留收到的模型消息、工具调用及模型侧完成状态。

哪些已实现，哪些仍然不可靠

已经打通的闭环

真实 OmniGibson 场景 → 四向 RGB → Astra 工具决策 → 动作执行 → 新观测 → finish → 独立评分 → 记录与回放。

Original 有可读取 Skills、静态 GT 导航、受控携带和放置恢复；Official 已接通 14 类官方注册动作并初始化导航规划器；不表示 14 类都已在真实任务中验证成功。

仍不能宣称“完美小脑”

视觉点绑定、接近点筛选、放置采样、碰撞与原生 IK 都可能失败。仿真本身还存在物理不稳定、GPU 内存耗尽或原生崩溃等故障。

省略低层电机控制，只减少一部分控制难题；不保证所有几何条件、语义状态、采样器和仿真运行都可靠。

我们额外设置了哪些限制，为什么会影响结果
限制初衷实际影响
最新 revision / 当前 image_ref防止拿旧画面操作已经移动的世界。即使机器人没动，重新 observe 后旧图也不能继续点。
80 动作 / 240 调用 / 20,000 env steps限制循环与资源消耗。任务可能在 30 分钟前耗尽其他预算；Skill 读取和观测查询也消耗调用数。
Original 的 1.4 m 距离、视野与局部候选保持操作范围与目标可见，避免走到错误表面。保守筛选可能把可操作目标判为没有合适接近点。
Original 的局部放置范围和 yaw 包络保留模型点选的层面，减少错误落点。候选不足或包络膨胀可能拒绝实际能够容纳的放置。
Official 单动作 120 秒 / attempts=1限制长时间采样，把外层重试留给大脑。原生 IK 和 settling 可能占满预算；执行期间的录像开销也会影响墙钟。

Official 的 120 秒预算在 generator yield 以及碰撞 / IK 调用边界检查，不能安全中断正在进行的单次 native / CUDA 调用，实际返回可能超过 120 秒。这些数值多数是项目的工程配置，不是 OmniGibson 自带的不可修改规律。RGB 数据边界和每任务 30 分钟来自实验要求；其他阈值需通过有针对性的任务验证来校准。

目前还没有：持续自动推送的并行感知、显式计划栈 / 长期记忆、从 RGB 建图的导航、完整动态碰撞规划、真实连续机械臂控制，以及所有故障的通用恢复机制。
