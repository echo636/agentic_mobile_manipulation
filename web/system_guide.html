02 / HARNESS & THE POLICY LOOP

Harness 是把大脑、工具和仿真接起来的运行层

模型负责决定动作；Harness 让这些决定能够可靠地执行、返回观测、留下记录并结束。MCP 是其中的工具通信接口，不是整个 Harness。

模型进程Astra / Codex CLI

维护模型会话与工具循环。读取图像，生成结构化工具调用，接收执行结果后继续推理。

prepare_project → run → parse
工具代理官方 SDK FastMCP

公布工具名称与 JSON Schema，接收调用，转发请求，将真实 RGB 图片组装成 MCP 图片内容。

当前批测用 stdio
仿真进程 · 单 owner 线程HTTP bridge → VisionHarness

bridge 排队；Registry 找到对应 handler，ToolContext 绑定本次调用。Harness 检查参数和图像版本，分发动作、刷新观测、写入结果。

只有仿真所属线程操作物理、渲染与状态
WHAT WE ALREADY HAVE

本轮补齐的公共组织层

  • 统一模型客户端：相同的准备、运行、解析接口。
  • 统一工具注册：schema、handler、profile 和元数据集中管理。
  • FastMCP：stdio、SSE、Streamable HTTP 三种入口。
  • 原生在线循环：另有 Responses 接口的 VisualToolLoop 与图像历史管理。
WHICH PATH IS ACTUALLY USED

实际验证范围要分开

真实批测主路径是 Astra + Codex CLI。工具循环由 Codex 客户端负责，不能把另写的 VisualToolLoop 画成它的内部组件。

OpenCode、Kimi 已有配置和解析适配；原生 Responses 循环也已实现，但这些路径尚未取得与 Codex 相同级别的真实任务验证。

一次工具调用穿过 Harness 的准确顺序
  1. 客户端从 FastMCP 获取 schema，并让模型按 schema 产生工具参数。
  2. FastMCP 经本机 HTTP bridge 递交请求与 request_id；网络线程不访问仿真状态。
  3. VisionHarness 校验工具是否在当前 profile、参数是否合法、revision / image_ref 是否仍有效；同 request_id 的重复 RPC 可以读取缓存结果。
  4. Registry handler 通过 ToolContext 调用观测、执行或结束操作。
  5. 执行器运行。一次动作尝试后 revision 增加，通常同步返回新的四向 RGB；部分失败也可能已改变世界。
  6. 代理下载并核对真实图片字节，再将文本与图片返回模型。模型据此选择下一步。
  7. finish 或统一期限触发收尾：合作式停止动作、取消待采集观测、owner 线程评分，随后完成视频与归档。

ToolContext 是可信 handler 的编程接口，不是任意 Python 代码的安全沙箱。当前也没有对模型开放任意代码执行工具。

三个容易混淆的层次：ToolRegistry 是工具定义与分发；FastMCP 是协议服务；HTTP bridge 是我们内部连接仿真线程的排队通道。支持内部 HTTP，不自动等于支持 MCP HTTP；现在三种 MCP transport 已专门实现并验证接口。
传输、多客户端与 Jinkai 的参考范围

使用官方 Python SDK mcp==1.28.1 中的 mcp.server.fastmcp.FastMCP。默认 stdio；HTTP 入口为 loopback 上的 /sse 和 /mcp。一个 Server 对应一个 episode，多客户端共享同一个机器人、观测版本、预算与结束状态，不会自动得到各自的仿真世界。

参考 Jinkai 导航 Harness 的客户端生命周期、统一注册、FastMCP 与在线循环组织方式。OmniGibson 的 owner-thread 调度、RGB 信息边界、执行器与私有评估由本项目维护，没有把 Habitat 环境直接接进来。

异步体现在 start / get / cancel 作业接口：提交不必等捕获完成。实际采集仍由仿真 owner 线程执行。它不是持续的视频感知流，也不能与正在执行的物理动作同时调用仿真器。一个动作结束后，还会同步采集并返回新的四向 RGB。新导航动作内部也会在 owner 线程的控制步之间采集私有深度更新地图；这些中途捕获不替换大脑持有的公开 image_ref，也不会自动推送给模型。

revision、capture 与 stale 的区别

revision 标记动作导致的世界版本；image_ref 标记一次捕获中的具体图片。重新 observe 即使没推进物理，也会替换当前有效图像引用。异步旧结果可保留，但 stale=true 的图不能继续作为新动作目标；新动作必须引用当前观测。

排队中的观测可以取消；已经进入渲染的原子捕获不能在内部任意位置打断。结束请求会取消待执行作业，避免评分前又进入一次不必要的背景渲染。

04 / TOOLS & SKILLS

Tool 是接口，primitive 是动作，skill 是工作方法

当前 Original 默认向模型开放 9 个工具。动作不是 10 个独立 MCP 工具，而是一个 act 工具中的 10 个 primitive 选项。

是谁决定调用哪个动作？Astra 选择工具名与参数，例如 act(primitive="grasp", target=…)。Registry 和 Harness 按这个名字分发；它们没有另一个隐藏的大脑替模型决定抓哪个物体。

4 份可读取的 skill

visual-manipulation

总体工作流程：观察 → 选择动作与目标 → 执行 → 核对新图 → 结束。

visual-exploration

用四向图像搜索目标，选择可见导航点，利用会话中的搜索历史。

pick-and-place

准备目标位置、抓取、搬运、放置，再检查是否放对。

failure-recovery

区分选点问题、不可达、采样失败和仿真故障，依据反馈调整。

read_skill 返回冻结的 SKILL.md 内容供模型阅读；读取 skill 不会自动执行一串动作。下一步仍由模型显式调用工具。目前没有单独运行的计划栈或长期记忆模块，会话历史仍然存在。

Original act 的全部动作与参数

navigate_to · grasp · place_inside · place_on_top · open · close · toggle_on · toggle_off · release · wait

共有参数：primitive、target、revision、placement_yaw_degrees、wait_seconds。最后两个选项不用时为 null。release / wait 的 target 为 null；其他动作使用当前图片上的归一化像素点。

look 是独立工具，支持 −90° 到 +90°，正角度向左转，输入当前 revision。它真的转动底盘；有四向相机并不意味着 look 用于采集四向图像。

06 / FROZEN ORIGINAL · HISTORICAL GT NAVIGATION

冻结 Original：视觉点提示 → 静态 GT 地图导航

版本范围：本节解释 Original 评测对照端 ac2995b 的历史方案。它保留用于解释既有结果；最新在线导航开发版见下一节，不再使用这张预生成可通行地图。

模型不提供路径，也不直接提供世界坐标。它选中的可能是桌面、书柜或地面；导航器根据这个视觉提示选择可站立、可达、能看到目标的接近点。

绿色：接近点 / 路径。算法示意，非真实任务地图或运行轨迹。

地图从哪里来？

读取 OmniGibson 场景提供、按机器人占地侵蚀后的静态 traversability map，转换为内部可通行栅格。它属于执行器的 GT 输入。

不是 RGB 建图，不是实时 SLAM。运行中会读取机器人真实位姿来跟踪路径；这不等于实时更新障碍地图。移动物体、开门和携带物体的完整动态碰撞尚未纳入地图。

机器人实际怎么移动？

自研 GreedyGridFollower 根据实际位姿给出下一小步 XY / yaw，按速度与转速上限约束；私有底盘适配器设置世界位姿并推进仿真，再读回实际位姿纠偏。

这属于有反馈的理想运动学控制，没有由模型输出轮速、关节力矩，也不是完整的物理底盘控制器。

候选点、最短路与路径检查的具体算法
  1. 像素反投影得到 WORLD 命中点，导航主要取其 XY 提示。
  2. 候选包含目标点、朝机器人方向退让约 0.7 m 的点，以及半径 0.3 / 0.6 / 0.9 / 1.2 m、每圈 12 个方向的点。
  3. 候选在最多 0.75 m 的范围内投影到可通行格；加入目标距离约束（≤1.4 m）和目标可见性筛选。起点必须在有效可通行区域，不把机器人传送到另一连通区域。
  4. 采用一次多目标 Dijkstra 搜索，不是 A*。八邻接栅格计算候选的可达性与测地距离；对角移动禁止穿过障碍拐角。
  5. 候选主要按 2×|目标距离−0.7| + 投影偏移 + 近原地惩罚 排序，测地距离用于可达性、排序平局等。不是简单选择距离机器人最近的格子。
  6. 路径做视线剪枝。规划、简化和逐步执行都使用相同的 supercover 检查，覆盖线段经过的每个格子，避免稀疏采样跨墙角。
  7. 跟踪路径并在末端朝向目标。每步实际位姿反馈参与纠偏；公开结果不暴露内部地图或 WORLD 路径。
最近的“转得很慢 / 已到附近却失败”修复了什么？

旧转向门限比仿真位姿残差还小，机器人会不断微转；任意细小位移又被误当成前进。新版允许合理朝向误差后平移，并根据朝目标的进展判断停滞。

另有两个精确复现的问题：末端转向不断沿用有微小偏差的实际 XY，导致误差累积越过 2 mm；距路点只剩 2–4 mm 时仍追逐变化的方位角。新版在末端保持固定目标 XY，并在单步范围内同时做有界平移与转向。

位置完成门限仍为 2 mm，最终朝向门限为 0.001 rad；没有放开速度或静态碰撞约束。代码仍用 20 个没有有效进展的反馈步检测停滞。真实失败路径的定向复验已通过，不代表所有场景和动态碰撞问题已解决。

和 Jinkai 的关系：参考其视觉点提示、接近候选、投影、可达性和排序策略。Habitat 的 navmesh / 原生 follower 在这里替换为 OmniGibson 静态栅格与我们自己的反馈跟踪器；不能把它们说成同一个导航后端。

07 / ONLINE DEPTH MAPPING · DEVELOPMENT C7F667F

新导航：从本轮深度观测建图，边移动边更新路径

大脑仍只看四向 RGB、仍用 navigate_to 点选画面目标。变化发生在私有小脑：不再读取场景预生成可通行地图，而是从当前 episode 的深度测量建立概率栅格，再用 A* 规划。

定位与建图要分开：地图来自新采集的深度；机器人 WORLD 位姿来自仿真器，作为理想定位输入。这里使用 Cartographer 的原生 ProbabilityGridRangeDataInserter2D 做概率更新，没有运行扫描匹配、回环检测或完整 SLAM 轨迹估计。
1 · 私有传感器四向深度 + 标定

同一冻结物理状态取得 depth_linear、K 和 WORLD 相机外参；按真正俯角与光心反投影。RGB 按原接口交给大脑，深度留在执行器。

机器人自身深度 → invalid / no-ray
2 · 原生 CPU 建图Cartographer 概率地图

用真实测量的 hit / miss 射线更新本轮地图，保存 free / occupied / unknown。无效深度不生成自由空间；机器人位姿只用于定位。

新测量 + 理想定位 → 私有地图快照
3 · 规划与执行A* + 分段重规划

按真实底盘占地膨胀障碍与未知区域。选择目标附近站位，沿观测到的自由区移动；约每 25 cm 或 15° 获取新深度并规划。

未知区域阻挡；不回退到 GT 地图

深度怎样变成可用于导航的测量？

  1. 用完整 K / WORLD 外参反投影，保留各相机真实光心。
  2. 把离当前地面约 0.15–1.25 m 的表面当作障碍候选；地板测量提供可见射线的自由证据。
  3. 过滤落在机器人自身 link 视觉凸包内的点。过滤只得到“无测量”，不会补成最大距离射线，也不会清空脚下地图。
  4. 同一方向近处障碍优先；range 截断与 invalid 深度分别处理。采用标准二维射线投影假设，不能宣称已验证整列高度均无障碍。

为什么调整四相机位置？

历史 rig 的光心位于半径 35 cm 处并向外看，机器人中心附近天然存在不可观测区；把它直接填成可行走区域会伪造证据。

新分支将四相机的 XY 光心放在机器人中心，保持四个方向、90° FOV、20° 俯角和同次捕获。实际外参与原始图像都保留；自身身体遮挡通过私有深度过滤处理。

这个相机变化属于新实验配置。历史 055 回放与原 100 条结果仍使用其原始 rig，不改写为新配置。

一次 navigate_to 的准确执行顺序
  1. 沿用公开图像版本校验和像素绑定，确定模型所选的 WORLD 提示点。
  2. 在仿真 owner 线程渲染四向深度，复制标定、位姿与自身几何；原始公开图像引用保持不变。
  3. 把私有射线交给独立 CPU worker；从空的本轮地图开始增量更新。按机器人真实底盘 / 轮部几何估计占地，不人为清除起点圆盘。
  4. 在观测到的自由区使用八邻接 A*；禁止跨障碍拐角，并保留路径线段碰撞检查。未知区也按阻挡处理。
  5. 沿路径执行有界位姿小步。位移约 25 cm 或转向约 15° 后重新采集、更新地图，并向原先选定的站位重规划。
  6. 没有观测到连通路线时返回导航失败，不能调用静态 GT 图补路线。成功到站后返回新 RGB；不把内部地图或路径作为额外模型观察。

底盘仍使用理想运动学位姿执行与实际位姿反馈，不是轮速控制。二维地图、有限视野、载物包络和动态物体仍有局限；不能据此称作完美小脑。

怎样确保没有偷偷使用预生成地图？原生依赖修复了什么？

ObservedNavigationScene 直接跳过预生成 traversability map 的加载入口，并拒绝读取 trav_map。导航只接收当前建图 worker 的快照，没有静态图 / NavMesh 回退；任务和物体的正常加载仍由 OmniGibson 处理。

在线结构参考同一上游仓库的 jiarui/memory-slam@136950b，它与 jinkai/harness@0815cf2 的 NavMesh 路径不同。这里复用了建图 / 占用栅格规划思路，重新适配 OmniGibson 的传感器、定位和执行；没有接入上游图记忆或给大脑额外地图。

原生建图接入时发现旧 Cartographer 静态库与新 worker 的 Eigen 头文件版本不一致，出现“能链接、测量却损坏”的 ABI 故障。现在使用匹配的 Eigen 3 头文件，并把 worker 与运行依赖放进本项目独立 runtime，未修改旧导航环境。

近期命中能立即阻挡新障碍；障碍消失要有重复的有效自由射线证据，不能仅因时间流逝把未知区域清空。这类动态更新与栅格边界已纳入原生建图测试。

验证状态 · c7f667f：35 项 CPU 集成 / 项目测试与 9 项真实原生建图测试通过。真实 GPU 导航组件正在运行；完整 Astra 任务尚待验证。这里没有把合成几何测试展示为真实场景地图，也没有将组件通过记作 BEHAVIOR 成功。

09 / EVALUATION & OPERATIONS

动作完成、模型声称成功、官方目标满足，要分开看

执行器报告

act completed

这一次操作通过了执行器的完成检查；只代表局部动作，不代表整个任务完成。

模型判断

finish achieved

模型根据图像和反馈认为做完了。它是任务完成主张，不能覆盖真实评估结果。

独立评估

BDDL / TaskMetric

结束后检查真实目标谓词，记录官方指标与 Q。全目标满足还需要结合任务截止时间判定本项目的终态。

例如书籍归架要求三本书都处于书柜内。把其中一本成功 place_inside 只完成了一个局部操作；模型需要继续处理其余书。最终评分由实际状态决定，不能因为模型说“全部完成”就记为成功。

任务队列怎么运行

任务列表固定到 task / instance / seed / 指令与版本。多个 worker 经主机内存和 GPU 资源准入后按队列领取任务，各自运行一个独立仿真 episode；完成顺序可以不同。

监督器负责初始化进展、任务期限、异常终态、收尾与资源释放。某条失败不应停止整条队列；每条都要有 success / failure / timeout 的结果。

记录和回放怎么对应

保存原始模型事件、工具参数和结果、图像、仿真控制步、视频、评分与版本，再把它们映射到同一回放时间轴。

模型文本展示实际返回的公开消息和 reasoning summary 原文。没有返回的内部思维不能补写；第三人称图像只服务于回放。

11 / A DISCUSSION-READY EXPLANATION

汇报时，沿着这五句话展开

① 我们在研究什么：在 OmniGibson 的 BEHAVIOR 操作任务上，研究一个通过 RGB 自主决策、调用工具、依据新观测纠错的 Agentic System。先用理想化小脑替代低层控制训练。

② 大脑怎么运行：Astra 经 Codex 客户端读取前后左右四张 RGB 和历史反馈，选择工具、primitive 与像素目标；默认不加入显式规划栈和长期记忆。

③ Harness 做了什么：统一客户端和工具注册，用官方 FastMCP 接口连接模型，以单仿真线程组织执行与观测，管理版本、预算、记录、结束和独立评分。

④ 小脑怎么执行：新开发版使用私有深度生成在线概率地图，结合理想定位和 A* 导航；操作仍采用受控携带与采样放置。冻结 Original 使用静态 GT 导航，Official 调用官方 Symbolic primitives 的原生执行流程。

⑤ 现在能得出什么结论：历史完整任务已通过，新在线建图目前通过 CPU 与真实原生建图测试，GPU 组件仍在运行、完整 Astra 任务待验证。已有评测混有工具集与源码变化，不能据此直接评价新导航的任务成功率。

老师问：这和 Code as Policies 一样吗？
当前主路径输出的是结构化工具调用，act 的动作枚举由我们实现；不让模型自由写 Python 去组合或修改底层控制。Motor 探索已暂停。模型可通过连续多次调用组合行为，但这不等于本轮采用任意程序策略。
老师问：小脑用了真值，是不是违反 RGB-only？
实验中的 RGB-only 指 policy 的观测边界。大脑不拿对象列表、状态、GT 地图或 Q；小脑为了替代理想执行使用深度、标定和真值几何。应明确称作 RGB-only policy + privileged executor，不把它说成全系统纯视觉。
老师问：为什么不把 Official 叫做“完美小脑”？
官方提供的是有前置条件的符号动作实现。目标解析、碰撞检查、IK、采样和状态修改仍会失败，仿真也可能崩溃。直接设置状态可以省掉电机控制，但不能自动满足所有几何与任务条件。
老师问：我们是实时建图吗？导航是 A* 吗？

老师问：异步 Tool 是否实现了同时看、同时动？
目前提供异步作业 API，模型或其他进程可以继续工作；但仿真读取与修改都在同一个 owner 线程，不能在动作内部并行采集。持续自动推送观测还不是当前实现。
