## 评分正反例

在完整实例、同一独立原生评分器下检查，保存原始 `goal_options` 与最佳完整绑定。goal_options 是替代绑定，不是时间序列。

| 状态 | 预期 |
| --- | --- |
| 鸡肉入盒1、菠菜入盒2，两盒冷藏，全部餐具及托盘归位且门关闭 | 通过 |
| 交换盒1/盒2的食物，其余同上 | 通过 |
| 先携带有载托盘到厨房，再拆开完成相同终态 | 通过；不能因过程次序拒绝 |
| 水槽内餐具顺序、暂放位置不同，最终11项都成立 | 通过 |
| 两种食物同盒，另一盒空 | 失败，不合“分别装进两个盒子” |
| 盒1入冰箱但盒2留在台面 | 失败 |
| 食物掉出盒子，盒子仍在冰箱 | 失败 |
| 只送到一只杯子，第二只仍在托盘/台面 | 失败 |
| 茶匙仍在盘上，盘子在水槽内 | 按原生Inside实际值判定；若Inside接受这种合理嵌套则通过，不强制直接接触水槽 |
| 托盘进入其他符合指令的厨房餐具柜 | 必须通过；否则扩展绑定后再冻结 |
| 托盘留在柜外、放在柜顶或错误房间的容器 | 失败 |
| 曾关门但最终任一目标门开启 | 失败 |
| 初态两扇门关闭，其余物品未搬 | 整体失败；关闭两项单独成立 |
| 模型finish(achieved)，原生终态有任一必需目标未满足 | 任务失败，另记错误完成声明 |

若原生 Inside 的传递语义造成食物仍在水槽盘中却也被错误视作冷藏，或评分绑定与资产身份不符，先建立反例修复定义/绑定，不能用动作日志覆盖原生状态。所有目标在最终一次动作和静置后重查，不对动作中瞬时接触失效直接判失败。

## 正式回合前冻结

1. 两条风险链通过后，再制作完整模板、实例状态和独立 overlay/注册；检查重载后初态、门状态及 RGB 一致。
2. 原生 BDDL 解析、完整场景绑定、上表正反例、每目标动作链全部通过。新注册任务须核对 runner 如何选择场景/任务，不能仅增加一个目录就当作完成接入。
3. 短自主试跑只向模型提供指令、RGB、有限类别反馈和公开接口；模型自己建计划并显式导航。检查动作消耗后选预算，另立冻结配置；不因单轮失败放松目标。
4. 正式回合用独立输出目录，保持实际连续物理步与显式导航。原始RGB、事件、状态和视频完整；独立原生评分与协议审计分别报告，`official_task_success=null`。
5. 至少建立一个开发实例与一个预先冻结的独立留出布局。记录所有尝试和失败归因；探针通过或单轮成功均不推断成功率。
