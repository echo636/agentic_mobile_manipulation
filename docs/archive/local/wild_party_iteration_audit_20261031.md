# 为什么派对清理试跑到 r65 仍没有收敛

2026-10-31。本次是既有记录与迭代流程审查，不是 CUDA/导航故障的运行时根因诊断。读取启动配置、终态记录、专项报告与失败日志；未启动实验、停止进程或修改执行器。结论分别标明记录事实与工程判断。

**工程判断：这串试跑承担了大量平台开发工作，不能当作固定设施的 60 多次重复验证，更不能作为 60 多个可比较的 skill 样本。**

## 直接证据与原因

### 1. 起点是尚待构造的研究实例，开发范围很大

[专项报告](/mnt/data/home/sunyujie/robot_manipulation/experiments/wild_party_runtime_20261026/REPORT.md)说明：任务没有已安装的公开挑战实例；原任务含 30 项初态约束、14 项终态目标。保留布料、液体、材料清理、携物导航和多容器关系；精简场景仍含原房屋 267/595 个物体。构造和执行适配本身就是主要工作。

这解释了为什么会持续遇到不同层的问题，但不能单独为长期不收敛辩护。模型每轮走不同路径，暴露的物理与接口组合也不同；一次较长轨迹没有崩溃，只支持那次轨迹通过。

### 2. 已有探针，但验收范围没有覆盖正式模型路径

`executor_probe_r14` 达到原生 14/14，报告同时明确其使用私有对象句柄、绕过抓取距离和跨房间导航。后续 `probe_v62_clean_first` 也无 RGB 模型选择和跨房间导航。

这些探针有价值，验证的是局部效果与谓词。它们没有证明公开接口下的“看见目标→接近→抓取→携物通过→放置→退出”全链可行。正式模型回合继续承担发现未覆盖设施问题的工作。PRIVATE 14/14 不等于模型成功，这一点报告写得清楚；问题是这些覆盖限制没有充分约束后续运行安排。

### 3. 完整模型回合被反复用于检验局部修复，反馈慢且不保证触发

v62 修改放置回退后，r33 在到达相关操作前结束，r34 只 initialize 就结束，均不能验证该修复；之后才有明确触发回退的私有探针。

另一个例子是晚期卡住：r62 在 navigate 卡住后，v80 为导航添加墙钟超时；r63 又在 look 使用的转向路径卡住，v81 才扩展到该路径。见[日志 PARTY-062 至 065](/mnt/data/home/sunyujie/robot_manipulation/agentic_mobile_manipulation_7f388e4/docs/bugfix_journal.md#party-062--v80-bounded-navigation-wall-time-watchdog-prepared-from-r62-stall)。

工程判断：相关代码路径缺少足够系统的共同验收。修一处后，应先验证同类路径及明确触发用例，再投入完整模型回归。

### 4. “越过旧故障点”有时被过早解读成稳定性结论

报告记录 r37 没有 CUDA700，并将此表述为降低渲染刷新“可以避免”r36 的崩溃；r38 改速后又出现 CUDA700。不同策略轨迹和不同配置下的一次无崩溃，不能单独证明某候选消除了根因。

v55 候选禁用放置后的回收箱碰撞；v60 候选持物期间跳过原生 PhysX，并在 r31 暴露视频记录缺口。此类改动涉及执行语义与其他路径，即使最终目标谓词未改，也需要新协议范围和回归证据。它们可以是研究执行器设计，不能仅以“下一轮走得更远”作为晋级依据。

### 5. 配置与记录控制也确实出了错

[r65 终止记录](/mnt/data/home/sunyujie/robot_manipulation/experiments/wild_party_runtime_20261026/model_on_r65_astra_medium_no_long_manual_termination.json)明确写明：用户要求 `gpt-6.1-sol/low`，该次却使用 `gpt-6-astra/medium`，因错误模型配置终止并排除。随后有独立的 sol/low 启动文件。这不是仿真难度造成的问题，是启动前校验没挡住配置偏离。

`PROGRESS.json` 同时保留 `model_trials=37`、顶层 `frozen_source=execution_source_v62`，而末段运行状态引用 v81；已经有外部终止记录的 r65 astra 回合，`run/run.json` 仍写 running。这说明摘要字段存在不同时间的残留。不能据这些字段判断当前进程或最新有效配置；本审查不做进程存活判断。

### 6. 任务未完成和程序 bug 需要分开

[r64 原始终态](/mnt/data/home/sunyujie/robot_manipulation/experiments/wild_party_runtime_20261026/model_on_r64_astra_medium_lookwatch/run/run.json)记录 232 动作、24607 模拟步、11/14、正式 blocked；视频通过。剩余是两只杯子和马桶污渍。模型记录了多次接近不可达/超距，不能凭这一回合认定数学上无可行路径，也不能把整任务失败统一叫作新模拟器 bug。

存在真实进展：一些早期崩溃被越过，长回合能返回评分；同时，设施可行性、视觉选择与策略完成度仍有不同的待解决事项。

## 应怎样改变推进方式

以下是建议，尚未执行：

1. 把设施开发和 skill 对照分开列队。对照需要固定模型、档位、源码、场景、预算、工具和结束规则；设施版本变化后重新登记实验条件。
2. 针对现有瓶颈优先验证浴室完整接近链，以及含相同 RGB/视频配置的长时物理运行。局部探针需要覆盖真实接口限制；私有验收仍只算设施证据。
3. 局部修复必须有能触发原故障的检查，并运行相关路径回归。随机模型没走到故障点，记为“未验证”，不要把它当作一次有效修复验证。
4. 建议设定连续重复同类设施故障的转诊断门槛，例如连续两次出现就转最小复现，不继续靠完整自主重试碰运气。这是后续工程规则建议，不是本轮已执行的停机动作。
5. 用单一实验规格生成启动命令，并在分配 GPU 前断言模型、档位和 skill 条件；终止状态与摘要从原始事实自动汇总，避免人工摘要互相冲突。
6. 平台准入不要求模型必须完成任务。若关键链可执行、观测公平、执行稳定、评分正确，模型的有效失败应作为实验结果保留；不以不断换模型、加规则、改执行器追逐单次成功替代比较。

需要更早纠正的是反馈循环：让每次修复有明确的可判结果，让每次模型运行有独立的测量目的。增加轮数本身不能补上这两点。
