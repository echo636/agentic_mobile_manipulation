# Checked atomic actions

The RGB agent still selects one point in the latest four-camera snapshot. The executor grounds only that selected target, checks the held tool and reach, applies the simulator's object/material state, and verifies the result after settling. Tool completion is distinct from independent task success. `wait` remains a time-control utility outside the task actions.

| Added action | Required held object | Simulator effect |
| --- | --- | --- |
| `wipe` | Contact particle remover other than a broom/vacuum | Remove compatible `Covered` material |
| `sweep` | Broom with adjacency particle removal | Remove compatible floor `Covered` material |
| `vacuum` | Vacuum with projection particle removal | Remove compatible `Covered` material |
| `spray` | Ready, switched-on projection particle applier | Add the applier's material to the selected object's `Covered` state |
| `spread` | Object already `Saturated` with material | Transfer that material to the selected object's `Covered` state |
| `soak` | Absorbent particle remover | Set `Saturated` from the selected producing source or filled container |
| `cut` | Slicer | Run the official `SlicingRule` or `DicingRule` transition on the selected object |
| `hang` | Movable item | Use the same verified `AttachedTo` operation as `attach`, with a selected nail/hook/hanger |
| `pour` | Liquid container | Transfer the selected water system through official `Filled` / `Contains` state setters |
| `place_near_heating_element` | Heated container | Place the carried container with OmniGibson's official heating-element primitive |

The ideal spray actuator targets the object selected in RGB. Upstream `ParticleApplier` appends a physical projection-overlap condition to its tool-state conditions; the executor omits only that overlap condition because it does not move the held nozzle through a physical spray trajectory. Toggle, capacity and material conditions remain checked. These ideal material actions change the selected object's simulator state; they do not validate a physical tool path.

CPU tests cover the public catalog, preconditions, state changes, projection condition handling, cutting transition, and hanging dispatch. Task-level scripted OmniGibson trials on public instance 301 reached official task success for `wipe` (`clean_a_keyboard`), `cut` (`chopping_wood`), `sweep` (`sweeping_garage`), `spray` (`spraying_for_bugs`), `hang` (`hanging_pictures`), and `vacuum` (`vacuuming_floors`). Each successful trial has a continuous five-view video, recorded action/capture events, an independent official evaluator result, and a page generated by `scripts/build_review.py`; see the [internal scripted review](http://10.130.140.115:8769/task_review_index.html). They are scripted executor trials, not RGB autonomous policy runs. `soak` and `spread` have not reached official task success in the public 100-task set. This pinned set has no positive `Saturated` goal; its only positive `Covered` goals are `spraying_for_bugs` and `spraying_fruit_trees`, both supplied with sprayers. A suitable soak/spread BDDL task (`staining_wood_furniture`) has no public test instance in the pinned manifest, so it was not used as a substitute for a public benchmark result.

The added names also appear in the real MCP `act` input schema. The hot-drink chain has a strict single-task coverage check and a real no-demo smoke run; a full success claim requires a larger action budget and is not inferred from this smoke run. Existing independently audited material-action trials remain documented above. The acceptance contract, including the `gpt-6-astra`/`low` default for new trials and labeling of completed `high` trials, is in [atomic_action_experiment_requirements.md](atomic_action_experiment_requirements.md).

The supplied coverage page is an analysis input, not simulator authority. The pinned BDDL defines `hanging_pictures` with `attached`; `laying_tile_floors` with `ontop` and `nextto`; and `polishing_shoes` with removal of shoe `Covered(dust)` plus placement relations. Its classification of the latter two as `spread` tasks is therefore not used as implementation evidence. No 100-task coverage or success claim follows from adding action names.
